Credit Card Fraud Detection Project
Detailed Project Overview, Development Process, and Core Technologies
=====================================================================


1. Introduction
---------------

This project is a machine learning based Credit Card Fraud Detection system. Its goal is to identify whether a financial transaction is legitimate or fraudulent by learning patterns from historical transaction data. Fraud detection is one of the most important real-world applications of machine learning because fraudulent transactions are rare, costly, and often difficult to detect using simple rule-based systems alone.

The project starts from a notebook-based exploratory analysis and extends into a reusable Python workflow script. Together, these two parts make the project both educational and practical:

- The notebook explains the analysis and modeling process step by step.
- The standalone Python script turns that process into a reusable pipeline that can be executed again whenever needed.

This project is useful for:

- academic demonstration of a machine learning classification workflow
- understanding imbalanced data problems
- showing how fraud detection systems can be built in practice
- presenting both analysis and implementation in one project


2. Problem Statement
--------------------

The main problem solved by this project is binary classification:

- Class 0 means the transaction is legitimate
- Class 1 means the transaction is fraudulent

The challenge in fraud detection is that the dataset is highly imbalanced. Legitimate transactions are extremely common, while fraudulent transactions are very rare. This creates a real machine learning challenge because a model can appear accurate simply by predicting most transactions as non-fraud. Therefore, the project does not rely only on accuracy. It uses more meaningful fraud-focused metrics such as:

- precision
- recall
- F1 score
- ROC-AUC
- PR-AUC
- balanced accuracy

This makes the project more realistic and more aligned with how fraud detection systems are evaluated in real business settings.


3. Dataset Used
---------------

The project primarily uses the file:

- creditcard.csv

It also contains additional files in the archive folder:

- archive/fraudTrain.csv
- archive/fraudTest.csv

These two files are an alternative IEEE-CIS fraud dataset that was downloaded for reference and
potential future comparison experiments. They are not used in the main analysis. The primary
analysis uses creditcard.csv.

The main working dataset is the well-known credit card fraud dataset where most original input columns are anonymized for privacy. The columns usually include:

- Time
- V1 to V28
- Amount
- Class

Explanation of the important columns:

- Time:
  Represents the number of seconds elapsed between each transaction and the first transaction in the dataset.

- V1 to V28:
  These are anonymized numerical features obtained through dimensionality reduction techniques. Their original meanings are hidden for privacy reasons, but they are still useful for machine learning.

- Amount:
  The transaction amount.

- Class:
  The target variable. It indicates whether the transaction is fraud or not.

One of the most important observations in this dataset is the fraud imbalance. Fraud cases form only a tiny percentage of the total data. This means the project must handle class imbalance carefully during modeling and evaluation.

5. How The Project Was Made
---------------------------

The project was developed in multiple stages. Each stage adds more functionality and makes the final system stronger and more useful.


Stage 1: Basic Data Understanding
---------------------------------

The first step in building any machine learning project is understanding the data. In this project, the dataset is loaded using pandas and inspected using:

- head()
- shape
- info()
- isnull().sum()
- value_counts()

This stage helps answer the following questions:

- How many rows and columns are in the dataset?
- Are there any missing values?
- What is the distribution of fraud vs legitimate transactions?
- Is the dataset balanced or imbalanced?

During this stage, class distribution is also visualized using plotting tools so that the fraud imbalance becomes easy to understand visually.


Stage 2: Baseline Machine Learning Model
----------------------------------------

After understanding the data, a baseline model is created. This is important because every stronger solution should be compared against a simpler starting point.

The baseline model in the project uses:

- train_test_split from scikit-learn
- StandardScaler for feature scaling
- LogisticRegression for classification

The baseline model pipeline works like this:

1. Separate the input features and target label.
2. Split the data into training and testing subsets.
3. Standardize the feature values where needed.
4. Train the logistic regression model.
5. Predict the target values on the test set.
6. Evaluate using confusion matrix and classification report.

This part of the project demonstrates the standard supervised learning workflow and provides a clean first result.


Stage 3: Premium Modeling Upgrade
---------------------------------

The project was then improved into a more advanced fraud detection system. This is where the notebook and script become much more practical. Instead of stopping at one simple model, the project introduces:

- feature engineering
- model benchmarking
- threshold tuning
- business-focused metrics
- alert prioritization

This upgrade is important because fraud detection in practice is not only about whether a model can classify correctly. It is also about:

- how many frauds it can catch
- how many false alerts it creates
- how suitable it is for investigation teams
- how well it ranks risky transactions


6. Data Preparation and Splitting
---------------------------------

The project prepares the data in a clear machine learning format.

- X contains the input features
- y contains the Class label

The enhanced workflow uses a more realistic split strategy:

1. A clean test set is separated from the full data.
2. The remaining data is split again into training and validation sets.

Purpose of each split:

- Training set:
  Used to fit the machine learning models.

- Validation set:
  Used to compare candidate models and choose the best threshold.

- Test set:
  Used only at the end for final evaluation so performance remains honest.

The split is stratified. This means the same fraud proportion is preserved across train, validation, and test sets. Stratification is especially important for imbalanced datasets like this one.


7. Feature Engineering
----------------------

Feature engineering is one of the strongest parts of this project. Instead of using only the original columns directly, the enhanced workflow creates additional features that help the model learn better fraud patterns.

Features created from Time:

- Hour
  The hour of day is extracted from the raw Time value.

- Hour_Sin and Hour_Cos
  These encode time in a cyclic way so the model understands that hour 23 and hour 0 are close to each other.

- Period-based features
  Time of day can be grouped into categories such as morning, afternoon, evening, and night.

Features created from Amount:

- Log_Amount
  Applies a logarithmic transformation to reduce skewness in transaction amounts.

- Sqrt_Amount
  A square-root transformation that also helps normalize transaction amounts.

- High_Value_Flag
  Marks transactions above the 95th percentile.

- Extreme_Value_Flag
  Marks transactions above the 99th percentile.

- Amount_Percentile
  Tells where the amount lies relative to the rest of the dataset.

- Amount_ZScore
  Standardizes the amount compared with the full amount distribution.

Features created from anonymized V columns:

- V_Mean
  Mean of all V features for a row.

- V_Std
  Standard deviation of all V features for a row.

- V_Abs_Max
  Largest absolute V value in a row.

- V_Positive_Count
  Number of V features with positive values.

- V_Negative_Count
  Number of V features with negative values.

Why feature engineering matters:

- It gives the model richer patterns to learn from.
- It makes subtle fraud behaviors easier to separate.
- It improves ranking and classification quality.
- It makes the project feel more like a real machine learning solution instead of a basic tutorial.


8. Core Machine Learning Models Used
------------------------------------

The project compares multiple classification models instead of depending on only one.


8.1 Logistic Regression
-----------------------

Logistic Regression is used as a reliable and interpretable baseline. It is simple, fast, and often performs surprisingly well on structured numerical data.

Why it is used:

- easy to train and explain to a non-technical audience
- good baseline for comparison against tree-based models
- works well with scaled numerical features
- supports class_weight for imbalanced data

In the project, Logistic Regression is used with:

- StandardScaler
- class_weight="balanced"
- sufficient max_iter for convergence

Important note on threshold-0.50 performance:

When class_weight="balanced" is used, Logistic Regression adjusts its internal decision boundary,
which means raw probability scores shift away from 0.50. As a result, the model's F1 score at a
fixed 0.50 threshold appears low (around 0.096), while its recall is very high (0.879) and its
ROC-AUC remains strong (0.962). This is expected behavior. After threshold tuning on the validation
set, Logistic Regression's F1 improves significantly. It should not be judged by its 0.50-threshold
F1 alone.


8.2 Random Forest
-----------------

Random Forest is an ensemble machine learning model based on many decision trees. Each tree learns a different view of the data, and the final prediction is made by combining them.

Why it is used:

- captures non-linear relationships
- handles complex interactions between features
- often performs well on tabular data
- supports class imbalance handling through class weighting


8.3 Extra Trees
---------------

Extra Trees, or Extremely Randomized Trees, is another tree-based ensemble model. It is similar to Random Forest but introduces more randomness when constructing trees.

Why it is used:

- powerful on structured datasets
- often produces strong classification performance
- can rank feature importance
- useful for detecting complex fraud patterns

In the current project run, Extra Trees became the winning model in the enhanced workflow.


9. Why Class Imbalance Is Important
-----------------------------------

Fraud detection datasets are naturally imbalanced. This means:

- legitimate transactions are the majority
- fraud transactions are a very small minority

If we simply train a model and optimize only for accuracy, the model may predict almost everything as legitimate and still appear to perform well. That would be misleading and not useful in a real fraud detection environment.

To address this challenge, the project uses:

- stratified train/validation/test splits
- balanced class weights in models
- threshold tuning
- precision and recall based evaluation
- PR-AUC as an important metric

This is one of the reasons the project is stronger than a simple beginner classification project.


10. Threshold Tuning
--------------------

One of the best upgrades in this project is threshold tuning.

Normally, binary classifiers classify a transaction as fraud when the predicted probability is at least 0.50. However, in fraud detection this fixed threshold is often not ideal. A lower threshold may catch more fraud cases but also create more false alarms. A higher threshold may reduce false alarms but miss important frauds.

Therefore, the enhanced workflow:

1. Computes fraud scores on the validation set.
2. Tests many threshold values from low to high.
3. Measures F1 score, precision, recall, and balanced accuracy for each threshold.
4. Selects the threshold that gives the best fraud detection tradeoff.

This makes the project more realistic because operational fraud systems often use tuned thresholds instead of fixed defaults.


11. Model Evaluation Strategy
-----------------------------

After choosing the best model and threshold, the project evaluates the final system on the test set.

The following metrics are used:

- Confusion Matrix
  Shows true positives, true negatives, false positives, and false negatives.

- Precision
  Out of all predicted frauds, how many were actually fraud.

- Recall
  Out of all actual frauds, how many the model successfully detected.

- F1 Score
  Harmonic mean of precision and recall. Useful when balancing both is important.

- ROC-AUC
  Measures how well the model separates the two classes overall.

- PR-AUC
  Especially useful for imbalanced classification because it focuses more on the positive class.

- Balanced Accuracy
  Gives a better view than normal accuracy when classes are highly imbalanced.

The current enhanced workflow generated strong final test results, including:

- ROC-AUC around 0.9738
- PR-AUC around 0.8750
- F1 score around 0.8619
- recall around 0.7959

These results show that the system performs strongly on the fraud detection problem.

15. Internal Logic Of The Enhanced Script
-----------------------------------------

The enhanced_fraud_workflow.py script follows a structured machine learning pipeline.

Major internal steps:

1. Parse command-line arguments
   The script accepts dataset path, output directory, and top-k alert size.

2. Load dataset
   The script reads the CSV and validates important columns.

3. Build engineered features
   New features are created from Time, Amount, and V columns.

4. Split data
   The data is divided into train, validation, and test sets using stratified sampling.

5. Benchmark multiple models
   Logistic Regression, Random Forest, and Extra Trees are trained and compared.

6. Select best model
   The best model is chosen mainly based on validation PR-AUC and ROC-AUC.

7. Tune threshold
   Validation scores are used to search for an improved fraud detection threshold.

8. Evaluate on test set
   The final model produces scores and predictions on unseen data.

9. Create business outputs
   The script saves reports, charts, and alert tables.

10. Print summary
    The script prints a final concise result summary for the user.
